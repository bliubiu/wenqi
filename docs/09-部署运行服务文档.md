## 1. 文档定位

本文档面向开发与运维人员，说明项目的三种运行形态、数据底座的日常运维、构建部署流程与故障排查。架构原理见 03 号文档，存储设计见 06 号文档。

**三种运行形态**：

```
① 本地开发运行    bun run dev            → Next.js 开发服务器（http://localhost:3000）
② 数据管道运行    bun run data:all       → raw 数据清洗入库 → SQLite 唯一真相源 → 前端 JSON 导出
③ 静态分发部署    bun run build          → Next.js 静态导出（out/），CDN / Vercel / Netlify 分发
```

**核心原则**：SQLite 数据库（`data/wenqi.db`）是项目数据的唯一真相源；前端消费的所有 JSON 均由 `db:export` 从数据库导出，禁止手工编辑前端数据文件。

## 2. 环境要求

| 依赖 | 版本要求 | 用途 |
|------|---------|------|
| bun | ≥ 1.0（推荐最新稳定版） | 前端依赖管理、数据管道脚本（内置 `bun:sqlite` 驱动数据底座） |
| Rust | stable 工具链 | 编译 WASM 计算模块（`crates/wenqi-core`） |
| wasm-pack | 最新稳定版 | WASM 构建（仅修改 Rust 代码时需要） |
| Node.js | ≥ 18 | Next.js 运行时 |

> 禁用 npm 包管理，统一使用 bun（详见 AGENTS.md 约束）。

**安装**：

```bash
bun install        # 安装前端依赖
```

## 3. 本地开发运行

```bash
bun run dev        # 开发服务器，访问 http://localhost:3000
bun run build      # 生产构建（静态导出 out/，构建后自动执行 db:export 刷新数据）
bun run start      # 以 Next.js 服务器模式运行构建产物
bun run test:run   # 运行全部单元测试（vitest）
bun run lint       # ESLint 检查
```

**前置条件**：`public/data/processed/` 下必须存在前端数据（首次克隆仓库后先运行一次数据管道，见第 4 节）。`public/wasm/` 与 `public/data/` 均不入库（.gitignore），需要本地生成。

## 4. 数据底座运维

### 4.1 数据库概览

| 项目 | 值 |
|------|-----|
| 数据库文件 | `data/wenqi.db`（WAL 模式，当前约 172 MB） |
| 事实规模 | 诗人 14,139 位 / 作品 345,341 首 / 评分 14,139 条 / 节点 14,139 个 |
| 作品分表 | 按诗人朝代切片：`works_pre_qin`、`works_han`、`works_wei_jin`、`works_tang`、`works_five_dynasties`、`works_song`、`works_yuan`、`works_ming`、`works_qing`、`works_modern`、`works_other`（兜底表），每表含 `poet_id` 索引 |
| 辅助表 | `poets`、`scores`（三气评分）、`nodes`（星系节点）、`spatial_index`（KD-Tree）、`meta`（版本元数据）、`import_log`（管道阶段审计） |
| schema 管理 | 由 `scripts/db-core.ts` 统一定义，所有管道脚本共用 |

**meta 关键键**：`schema_version`、`dataset_version`（数据集版本）、`algorithm_version`（评分算法版本，当前 v1.1）、`generated_at`、`poets_count`、`works_count`、`scores_count`、`nodes_count`。

### 4.2 数据管道（全量重建）

```bash
bun run data:all
```

等价于依次执行：

| 阶段 | 命令 | 输入 → 输出 | 实测耗时 |
|------|------|------------|---------|
| ① 数据加工 | `bun run data:process` | `data/raw/chinese-poetry`（原始数据集）→ 写入 poets 表 + works 分表 | 约 25s |
| ② 三气评分 | `bun run data:score` | 读 poets/works 表 → 写回 scores 表 | 约 21s |
| ③ 空间索引 | `bun run data:index` | 读 scores 表 → 写回 nodes / spatial_index 表 | < 1s |
| ④ 归一化映射 | `bun run scripts/gen-t2s-table.ts` | 语料唯一字符 + OpenCC → 生成简繁归一化映射表（约 2600 对） | < 30s |
| ⑤ 全文检索索引 | `bun run data:search` | 读 works 分表 → 检索库 `data/search.db`（FTS5，简体归一化）+ 前端检索分片（v2） | 约 130s |
| ⑥ 数据导出 | `bun run db:export` | 读 DB → 写出前端全部 JSON | 约一分钟量级（1.4 万个分片文件） |

各阶段完成后均写入 `import_log`（含 stage、耗时、行数），可用 `db:stats` 查看。管道具备幂等性：重跑即以最新 raw 数据全量重建。

### 4.3 数据底座 CLI

```bash
bun run db:export    # 从 DB 导出前端全部 JSON（顶层清单 + 按诗人作品分片）
bun run db:dump      # 从 DB 导出 poets.json / works.json 调试快照（--out 指定目录）
bun run db:stats     # 查看表行数、版本元数据、管道阶段审计
bun run db:import    # 从 JSON 快照恢复 DB（历史快照重建通道，主管道不使用）
```

**`db:export` 产物结构**（输出至 `public/data/processed/`）：

```
public/data/processed/
├── manifest.json              # 数据集版本清单（对顶层文件记录 sha256）
├── poets.json                 # 诗人全量（约 6.5 MB）
├── scores.json                # 三气评分全量（约 11 MB）
├── nodes.json                 # 星系节点全量（约 6.4 MB）
├── spatial-index.json         # KD-Tree 空间索引（约 10 MB，供 WASM 邻近查询）
├── search/                    # 全文检索分片（16 桶 + 诗人字典，合计约 29 MB，首搜懒加载）
│   ├── manifest.json          # 检索索引清单（v2 / 归一化方式 / workCount）
│   ├── dict-poets.json        # 诗人 ID 字典（条目以序号引用，压缩体积）
│   ├── shard-0.json
│   └── shard-15.json          # 每条为 [诗人序号, 归一化小写标题, 归一化小写文本前16字]
└── works/poet/                # 作品按诗人分片（256 桶目录）
    ├── manifest.json          # 分片清单（strategy: by-poet, bucketCount: 256）
    ├── 00/poet_00039756-….json
    └── f7/poet_f78aa699-….json   # 路径可由 poetId 推导：works/poet/{uuid前2位}/{poetId}.json
```

**分片加载契约**：前端 `DataLoader.loadWorkShard(poetId)` 按上述路径推导拉取（平均约 11 KB/片），分桶算法与分表映射由 `src/infrastructure/data/shard.ts` 统一定义，前端与管道共用同一份真相。

### 4.4 常用运维场景

| 场景 | 操作 |
|------|------|
| raw 数据集更新后同步 | `bun run data:all`（全量重建 + 导出） |
| 仅调整评分算法后重算 | 修改 `scripts/calculate-scores.ts`（记得更新 `SCORING_ALGORITHM_VERSION`）→ `bun run data:score && bun run db:export` |
| 检查数据完整性 | `bun run db:stats`（核对各表行数与 meta 计数、查看阶段审计） |
| 排查某位诗人数据 | `bun run db:dump --out data/tmp-dump` 后检索快照 JSON，或直接 SQL 查询 works 分表 |
| 构建产物数据刷新 | `bun run build` 自带 postbuild 导出；也可单独 `bun run db:export` |

## 5. WASM 计算模块构建

`crates/wenqi-core` 为 Rust 计算层（三气评分、空间索引、全文检索、聚类、bincode 编解码），编译为 WASM 供浏览器调用：

```bash
bun run build:wasm    # wasm-pack 编译 → public/wasm/（wenqi_core_bg.wasm 等）
```

- 仅在修改 Rust 源码后需要重新构建；仓库分发以预编译产物为准。
- 浏览器端由 `src/infrastructure/wasm/bridge.ts` 初始化（低频 JSON 通道 + 中频 bincode 双通道），初始化失败自动降级为纯 JS 实现（见第 7 节）。
- Rust 测试：`cargo test`（位于 `crates/wenqi-core`）。

## 6. 构建与部署

### 6.1 构建产物

```bash
bun run build
```

- Next.js 静态导出至 `out/`（纯客户端 SPA，无服务器运行时）。
- postbuild 钩子自动执行 `db:export`，保证构建产物携带最新数据。
- 产物体积的主要构成：Three.js 渲染引擎、前端 JS、WASM 模块、前端数据 JSON。

### 6.2 部署目标

纯静态分发，支持 Vercel / Netlify / 任意静态 CDN：

| 要点 | 说明 |
|------|------|
| 入口 | `out/index.html`（单页应用） |
| 数据目录 | `out/data/processed/` 随站点分发 |
| WASM | `out/wasm/` 随站点分发，MIME 类型需支持 `application/wasm` |
| 运行时依赖 | 无后端、无账号系统；配置存 localStorage，缓存存 IndexedDB |

### 6.3 缓存策略建议

| 资源 | 建议策略 |
|------|---------|
| `data/processed/works/poet/**`（分片） | `immutable, max-age=31536000`——分片内容随数据集版本变化，重新部署即全量换新 |
| `manifest.json` | 短缓存（如 `max-age=300`），作为版本探测入口 |
| `poets/nodes/scores/spatial-index.json` | 与 manifest 同策略或中等缓存 |
| `wasm/*.wasm` | 长缓存（文件名含内容哈希时可用 immutable） |

前端 IndexedDB（`WenQiDataCacheV1`）会缓存已加载的 JSON（含作品分片），配合 `dataset_version` 实现版本失效（见 06 号文档版本契约）。

### 6.4 性能基线与已知瓶颈

以下指标目标出自 01 规格书 4.1 节（桌面端首屏 ≤ 3s、节点渲染 60fps、搜索 < 200ms）：

| 项 | 现状 |
|-----|------|
| 首屏初始化数据 | poets + nodes + scores 三份 JSON（合计约 24 MB，未压缩；CDN gzip 后预计 6–8 MB）——首屏主要瓶颈，后续应引入分页/分片 |
| 作品详情 | 按诗人分片按需加载（约 11 KB/片）✅ 已达标 |
| WASM 初始化 | bridge 双通道，失败自动降级 |
| 渲染降级链 | WebGL 2.0 → Canvas 2D（`Canvas2DEngine`）→ 文字兜底（`TextFallbackEngine`），由 `RendererFactory` 按能力选择 |

## 7. 运行时组件与降级

| 组件 | 行为 |
|------|------|
| 渲染引擎 | `RendererFactory` 按浏览器能力选择 WebGL / Canvas 2D / 文字兜底，切换时 UI 显示 `RendererBanner` 提示 |
| WASM | `CompositionRoot.initialize()` 初始化失败仅记录日志，检索等用例走 JS 降级路径 |
| 数据缓存 | `DataLoader`：内存 Map → IndexedDB（`WenQiDataCacheV1`）→ fetch，逐级兜底；缓存写入失败静默忽略。**缓存键含数据集版本**（来自 manifest.json），数据重新发布后旧缓存自动失效，无需用户清理 |
| 日志 | Console + IndexedDB（`dbLogger`）双通道，内容脱敏（密码/身份证/手机号禁止明文），规范见 03 号文档第 6 节 |
| 错误兜底 | `ErrorBoundary` 包裹渲染异常；数据加载失败显示中文错误信息 |

## 8. 检索能力现状与演进

**现状**（PRD F07 主体已实现，e2e 已验证）：

- 诗人名检索：WASM 检索通道优先，降级为前端名称匹配；
- **诗句全文检索**：`bun run data:search` 构建独立检索库 `data/search.db`（FTS5 trigram，简体归一化，含 BM25 排序与摘要高亮），并导出 16 个前端检索分片（标题 + 文本前 16 字，诗人 ID 字典化，按作品 ID 哈希分桶，合计约 29 MB）；前端 `ShardSearchIndex` 首搜并行懒加载分片（经 IndexedDB 缓存，二次搜索零网络开销），线性匹配由 `SearchUseCase` 统一收口，命中作品跳转所属诗人并触发聚气；
- **简繁归一化**：语料为繁体古本，构建期以 OpenCC（`scripts/gen-t2s-table.ts`）生成语料驱动的简→繁单字映射子集（约 2600 对，已用 README/docs 简体文本反向过滤），索引与查询词两侧同变换——简体查询可命中繁体原文；映射表随数据集重建自动再生成；
- 检索召回可用 `bun run scripts/db.ts search <关键词>` 人工验证（≥3 字走 FTS5 MATCH，更短退化 LIKE）。

**实测性能**（bun 运行时基准，浏览器 V8 同量级）：34.5 万条最坏全量扫描约 65ms（构建期小写化 + 16 字截断后），远低于 PRD 的 200ms 指标；首搜额外承担约 29 MB 分片下载（生产 CDN gzip 后预计 8–10 MB）。

**已知限制与演进决策记录**：

- **分片内倒排（bigram postings）暂缓**：已实现并实测——JSON 键开销导致索引体积 29 MB → 100 MB（+240%），而线性扫描经小写化优化后已达标，收益不抵体积代价，故回退。数据量增长（>100 万条）或改用二进制索引格式时可重启该方案；
- **OpenCC 字级歧义**（如天干地支用字与卦象用字合并为同一简体形）：索引与查询两侧一致归一化，检索命中不受影响；搜索结果显示归一化词形（与作品原文的繁体词形存在字形差异），属 MVP 取舍；
- **匹配范围为标题 + 文本前 16 字**：完整原文检索需扩大截断或引入倒排/二进制索引，随规模演进；
- **远期选项**：SQLite WASM + OPFS 浏览器直查 FTS5（需重估包体积预算）、Rust WASM 紧凑倒排（`crates/wenqi-core/search.rs`）。

## 9. 故障排查

| 现象 | 原因与处理 |
|------|-----------|
| 首屏报「加载 xxx.json 失败」 | `public/data/processed/` 无数据——先运行 `bun run data:all`（或至少 `bun run db:export`） |
| 作品详情/搜索无作品数据 | `public/data/processed/works/` 分片缺失——重跑 `bun run db:export` |
| WASM 初始化失败 | `public/wasm/` 缺产物——执行 `bun run build:wasm`；功能自动降级不影响基础漫游 |
| `db:import` 报「数据源缺少 xxx」 | `data/processed/` 下无 JSON 快照——该命令仅用于快照恢复，主管道请使用 `bun run data:all` |
| 导出提示「作品数与 workCount 不一致」 | raw 数据与元数据存在偏差，建议重跑 `bun run data:all` 全量重建 |
| IndexedDB 缓存陈旧 | 数据集版本更新后前端自动失效；必要时在浏览器清除站点数据（IndexedDB `WenQiDataCacheV1`） |
| 构建后数据未更新 | postbuild 会自动 `db:export`；若手工绕过 build 脚本，请手动执行 `bun run db:export` |
| 分表出现 `works_other` 数据 | 存在未映射朝代的作品——检查 `src/infrastructure/data/shard.ts` 的 `DYNASTY_TABLES` 与 raw 数据的朝代代码 |

## 10. 命令速查

```bash
# 开发
bun run dev                      # 开发服务器
bun run build                    # 生产构建（含 postbuild 数据导出）
bun run test:run                 # 单元测试
bun run lint                     # ESLint

# 数据管道
bun run data:all                 # 全量：raw → DB（加工/评分/索引）→ 前端导出
bun run data:process             # 仅数据加工（raw → poets/works 分表）
bun run data:score               # 仅三气评分（DB 内）
bun run data:index               # 仅空间索引（DB 内）
bun run data:search              # 仅全文检索索引（FTS5 库 + 前端检索分片）

# 数据底座
bun run db:export                # DB → 前端全部 JSON
bun run db:dump --out <dir>      # DB → 旧格式调试快照
bun run db:stats                 # 数据库统计与管道审计
bun run db:import                # JSON 快照 → DB（恢复通道）
bun run scripts/db.ts search <词> # FTS5 召回验证（如：search "疑是地上霜"）

# WASM
bun run build:wasm               # Rust → WASM（修改 crates 后执行）
```
